# Mellyn Security: Governance & Control-to-Evidence Crosswalk

> **In plain terms:** AI agents can be manipulated by the text they read. Mellyn sits between an agent and the tools it uses, and it enforces fixed rules the agent cannot talk its way past. It decides what the agent may do alone and what needs a person's approval. It blocks data from leaving to unapproved places, and it records every decision in a log that shows any later tampering. This document maps those controls to NIST AI RMF, ISO/IEC 42001, SOC 2 and ISO/IEC 27001, and says what evidence proves each one works. It also states plainly what Mellyn does *not* cover, which remains the organization's job.
>
> *Framework IDs:* NIST AI RMF subcategories were checked against the NIST AI 100-1 Core tables on 2026-11-27. ISO/IEC 42001 Annex A titles were checked against a secondary control list and should be confirmed against a licensed copy of the standard before an audit.

## 1. System Scope & Governance Objective
Mellyn is a fail-closed runtime authorization and containment layer positioned between an AI agent and external Model Context Protocol (MCP) tools (`mellyn proxy` multi-server gateway and `mellyn-airlock` stdio containment proxy). Its governance objective is to enforce deterministic authority boundaries, prevent unauthorized data egress or tool-schema drift, and generate tamper-evident forensic logs for continuous assurance.

*Note: Mellyn provides technical enforcement and audit evidence across NIST AI RMF 1.0, ISO/IEC 42001, SOC 2 (Trust Services Criteria), and ISO/IEC 27001:2022. It does not replace organizational legal review, HR/physical controls, vendor contracting, or enterprise risk acceptance.*

## 3. Control Boundaries (Shared Responsibility)
To avoid compliance theater, Mellyn explicitly separates **enforced technical controls** from **organizational controls** that must live outside the proxy:

*   **Enforced by Mellyn (Technical):** Deterministic tool-call gating (`low`/`medium`/`high` + `[[scoped_rules]]`), stateful taint-based escalation, single-use exact-call human `ApprovalGrant`s gated by a separate `Role.APPROVER` key, cryptographic AgBOM/manifest pinning, NFKC/invisible-Unicode rejection, workspace path and domain egress confinement, fail-closed AAD disengagement, and redact-before-disk `schema_version = 2` hash-chained JSONL logging.
*   **Required Outside Mellyn (Organizational):** Named system ownership, business risk-tier approval, branch protection and PR review gates for TOML policy changes, HR/physical security, legal/regulatory notification SLAs, periodic access reviews, and formal return-to-service sign-off after an AAD kill-switch event. Mellyn itself is a single-maintainer project, so these organizational roles currently belong to one person, and that segregation-of-duties gap is recorded as `RSK-08` in [RISK_REGISTER.md](RISK_REGISTER.md).

## 4. Verification & Evidence Cadence
*   **On Every Policy or Engine Change:** Run `python -m unittest discover -s tests -v`, `mellyn bench --surface both --json` (confirming `0` false positives and `100%` canary recall), and the companion `mellyn-redteam` conformance suite to verify zero regressions.
*   **On Every MCP Tool Update:** Re-run `mellyn pin` (Gateway `tools_sha256` / `pinned_tool_hashes`) or `mellyn-pin` (Airlock `agbom_pins` / `manifest_sha256` / `instructions_sha256`) to audit schema diffs and explicitly re-pin approved tool definitions.
*   **Post-Incident / Bypass Discovery:** Reproduce the bypass in `mellyn-redteam` (and capture a regression vector in `tests/` / `mellyn-bench`), patch the control, verify the `mellyn-audit.jsonl` hash chain with `mellyn verify` / `mellyn-ir`, and archive the drill evidence in an incident report (see [INCIDENT_DRILL_001.md](INCIDENT_DRILL_001.md)).
